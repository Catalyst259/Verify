# 「验一下」技术栈与架构调研及一周黑客松实施建议

调研日期：2026-09-29。依据：[PRD](../验一下PRD.md)、[前端参考提取稿](reference/design-reference.txt)，以及本次确认的条件：**约一周开发、语言可选、暂无携程内部 API，可以采集互联网公开通知与评价**。团队人数和预算未确认；下文排期按 2–3 人协作估算，并提供单人调整方式。

本文是技术调研和设计建议，尚未实现或压测产品。公开网页与源码已实际读取；模型、搜索、地图的付费接口未做带密钥调用。性能、成本中的容量假设和验收指标均标为估算或目标。来源索引见[研究证据与访问记录](research/来源索引.md)。

## 1. 选型结论

建议采用 **React + TypeScript 的移动 H5，Python + FastAPI 后端，LangGraph 管理有界核验流程，PostgreSQL 保存任务、证据和结果；公开官网定向采集 + 搜索 API 发现来源 + 高德 POI/路线 API 提供证据**。用一个代码仓库和一个后端应用，部署为 HTTP 进程与后台 worker；不拆微服务。

模型优先试用百炼上的中文视觉模型与文本模型，通过统一调用接口保留替换能力。首个对照组可用 `qwen-vl-plus` 做截图提取、`qwen-plus` 非思考模式做文本抽取与解释；这是有官方文档支持的**起测组合**，并非声称其在当前全部模型中最优。第一天以真实旅行截图和证据样本比较账号实际可用的候选，随后冻结模型版本、提示词和输出结构。[S21] [S22] [S27]

核心投资应集中在 **POI/入口确认、Claim 结构、来源采集质量、时间场景对齐、反证检索、结论约束**。这些能力决定产品能否兑现 PRD；更大的模型、更多 Agent、更多引用本身不解决这些问题。

一周演示选择一个城市的 5–10 个 POI，完成每次 3–5 条 FACT / ROUTE / CROWD 核验。地域范围是交付建议，不能变成系统只识别预设截图：范围内的新截图仍要实时提取主张、检索并裁决；范围外也应正常解析，明确覆盖不足。真实联网、已采集快照、合成测试数据分别标记，不把回放包装成实时核验。

## 2. 从 PRD 推导出的架构要求

| 产品约束 | 必须落实的技术设计 | 容易走错的方向 |
|---|---|---|
| 嵌入携程决策链路 | H5 可嵌入；未来可接宿主身份、POI ID 和跳转；当前独立网页演示 | 一周内重建旅行平台或原生 App |
| 从截图/链接/文字进入 | 统一输入对象，保留原图、原文片段与出处；链接失败可补截图 | 要求用户先创建行程 |
| Claim 为最小单位 | 每条独立场景、证据、状态、结论和重试 | 对地点输出一个可信度分数 |
| FACT / ROUTE / CROWD 优先 | 三条不同证据路径，路由由类型和所需字段控制 | 所有问题都交给同一联网问答 |
| 主动反证 | 每条记录反证查询或结构化反证检查及其结果 | 只搜原句，搜到相似表达就通过 |
| 时间与场景对齐 | 区分抓取、发布、到访、适用日期；地点细化到入口/区域 | 把“今天抓取到”当作“今天有效” |
| 证据充分即停止 | 来源直接性、适用性、独立性和冲突状态决定继续检索 | 凑固定 3 个来源、多数票裁决 |
| CROWD 场景敏感 | 到访日期、星期、节假日、时段、入口和样本偏差进入判断 | 将评论发布时间、总评分当客流 |
| 结论→理由→证据 | 前端逐条卡片；引用精确关联 Claim 和原文片段 | 只在报告底部挂一串 URL |
| 部分失败可用 | 独立结果、失败原因、断线恢复和单条重试 | 一家网站超时导致整份报告失败 |
| 后续旅行决策 | 提取原始需求，按已核验证据解释替代 POI，提供真实落地页 | 用推荐打断核验；假装已完成预订 |

EXPERIENCE 和 MARKETING 在数据结构中保留类型，首周不套用事实真假标签：展示“暂不核验/需要定义观察指标”，不凭空把“宝藏”改写为“人少”。首周不做全网爬虫、假评论识别、完整传播链、自动预订、复杂个性化或统一评分，与 PRD 的排除范围一致。

## 3. 类似产品与开源系统：哪些事实已证实

对商业产品，仅将官网、API 文档和已保存的商店资料当作公开证据，**没有公开源码就不推断其内部语言、数据库或 Agent 框架**。对开源项目区分 README 的能力声明、依赖清单和许可证；这些只能证明公开实现，不证明部署表现或准确率。

这是一组直接相关的代表案例，不是全市场穷尽搜索，也不能据此声称市场上不存在同类功能。TripGenie 引用的是历史官方发布，不将当时宣传数据当作本项目转化率预测。

## 4. 候选方案的取舍

下表为基于当前约束的工程判断，不是实测排名。

| 方案 | 首周交付 | 旅行证据处理 | 调试与评估 | 主要代价 | 结论 |
|---|---|---|---|---|---|
| React + FastAPI + 明确状态图 | 好；需前后端联调 | Python 采集/抽取生态方便，规则清晰 | 类型对象、固定样本和节点日志容易定位 | 双语言、一个后台任务进程 | **推荐** |
| 全 TS：React/Next.js + Node + 显式状态机 | 好；团队偏 JS 时更快 | Playwright/Readability 足够，部分中文处理需额外选择 | Zod 与共享类型方便 | 长任务不宜直接依赖平台短时 Serverless 请求 | 团队明显偏 TS 时可等价替换，不必迁就 Python |
| Dify + 自定义工具后端 + H5 | 提示词试验快 | 复杂 POI/时间/证据逻辑仍在工具后端 | 流程可视化好，版本/评测跨两套环境 | 自托管依赖、DSL 与业务代码分散 | 备选；不同时维护代码图和平台图两套真相 |
| 直接 fork DEFAME / GPT Researcher | 很快得到通用演示 | 领域差距大；数据与报告结构都要改 | 原仓库依赖和默认行为需排查 | 看似复用多，真正需要替换核心路径 | 研究参考优于直接产品底座 |
| 全自主多 Agent + 向量库 + 微服务 | 首周风险高 | 自由规划不会自动解决来源/场景质量 | 重放难、成本和搜索次数不确定 | 部署、循环、协调及缓存一致性 | 暂不采用 |

**为什么前端选 Vite 而不是默认 Next.js：** 嵌入 H5 主要是交互式提交与结果，不依赖 SEO 或服务端渲染；后端已有 FastAPI，Vite 静态产物更少一层 Node 运行时。若团队熟悉 Next.js，也可用作前端，但不再增加一套 Node 业务后端。

**为什么仍选 LangGraph：** 本流程有地点确认暂停、按 Claim 并发、证据不足时有限补查、失败恢复，已具备有状态图的需求。[S15] 只用 `StateGraph`、持久化 checkpoint 和必要事件，不引入通用聊天记忆或无限 ReAct。若首日原型证明仅需单向流水线，可用 asyncio + 显式状态实现同一 Interface；不能因此省掉持久化与失效规则。

**为什么暂不选向量库：** 核验首先按 POI、日期、来源类型和入口过滤。首周几十到几百份候选文档，SQL 元数据过滤 + 关键词/BM25 足够；中文分词需显式配置，不能假设 PostgreSQL 默认全文检索天然处理好中文。第二阶段再对过滤后的候选加 embedding/重排，或用 pgvector；不要把整网抓取内容先灌向量库再让模型判断。

## 5. 推荐架构与模块接口

```text
移动 H5：输入 → 地点/日期确认 → 逐条进度 → 结果卡 → 证据弹层/后续行动
                          │ HTTPS + SSE
                          ▼
FastAPI：创建任务、确认上下文、读取结果、重试、发送已落库事件
                          │
PostgreSQL：任务/任务租约、Claim、Evidence、Verdict、事件、checkpoint
                          │
同仓库 worker：有界核验状态图
   输入提取 → POI 确认 → Claim 分类 → 按 Claim 并发
                                          │
              ┌───────────────────────────┼──────────────────────┐
              ▼                           ▼                      ▼
       FACT 官方/公告检索          ROUTE 地图/入口计算       CROWD 评价检索
              └───────────────────────────┼──────────────────────┘
                                          ▼
                  原文/响应留存 → 去重 → 场景匹配 → 支持与反证
                                          ▼
                      充分性检查 → 有预算则补查一次
                                          ▼
                     受约束 Verdict → 解释/排序 → 替代 POI

采集支路：白名单站点/公开页面 → HTTP 抽取 → 必要时浏览器渲染
                         → 文档快照与元数据 → 证据候选库
未来接入：携程产品/评价/交易信号 Adapter → 同一证据结构
```

### 5.1 部署选择

- 前端：React + TypeScript + Vite；组件保持移动卡片结构，可选轻量移动组件库，宿主 UI 接入前不假装采用了携程内部设计系统。
- 后端：Python 3.12、FastAPI、Pydantic v2、httpx；LangGraph 版本与 checkpoint 插件配套锁定。
- 数据：PostgreSQL 一套，JSONB 存类型特有字段，主键/关系/状态仍用明确列；SQLAlchemy + Alembic 管迁移。
- 文件：演示用受限目录及持久卷保存截图和获准保留的原文快照；需要多实例时迁移对象存储。对外仅提供短期授权访问，不开放整盘目录。
- 运行：Docker Compose 启动反向代理、API、worker、数据库；不额外引入 Redis、Kafka、Kubernetes。
- 观测：结构化日志 + 每节点耗时/工具状态/Token/引用 IDs；可选 tracing 产品，首周不强制增加一个自托管观测集群。

### 5.2 深模块与真实可替换处

这里采用 codebase-design 的 Module / Interface / Seam / Adapter 概念：把复杂度收在模块内部，只有真实存在不同实现的地方才设置可替换接口。

| Module | 对调用方的 Interface | 藏在 Implementation 中的复杂度 |
|---|---|---|
| InputUnderstanding | `understand(input) → candidates + raw_claims + source_spans` | 视觉/OCR、图片方向、链接解析、主张拆分、低质量识别提示 |
| PlaceContext | `resolve(candidates, user_context) → confirmed_place 或 needs_confirmation` | POI 别名、城市、区域、入口、地图 ID，用户修改后的版本 |
| EvidenceAcquisition | `collect(claim, context, budget) → evidence + gaps + trace` | 官方与网页检索、地图请求、采集、退避、去重、反证查询 |
| ClaimVerification | `verify(claim, evidence, policy) → verdict + cited_ids + limitations` | 时间场景、资格过滤、冲突、充分性、类别特有规则、表述约束 |
| ReportProjection | `project(run) → cards + summary + next_actions` | 排序、部分结果、证据关联、前端可读文案；不产生新事实 |

已有现实差异的 Seam：实时网页与已保存快照、HTTP 抽取与浏览器抽取、真实工具与测试 fixture。携程内部 Adapter 仅预留契约，不实现空壳“假 API”。避免一开始给每个步骤都创建插件体系。

LLM 负责提取、语义关联、证据立场建议和可读解释；代码负责金额/时间/距离单位、日期逻辑、证据 ID 存在性、调用预算、缓存失效和可输出结论集合。即使供应商支持严格 JSON Schema，业务引用与场景仍必须验证，结构合法不代表内容真实。

## 6. 数据模型：使证据可以审计，而不只是带一个链接

建议 8 类业务记录：`runs`、`inputs`、`claims`、`evidence_documents`、`claim_evidence_links`、`verdicts`、`events`、`jobs`；graph checkpoint 使用插件自己的表。地点评估集可从固定 JSON 导入，后续再独立 POI/entry 表。

| 对象 | 必须字段 | 不变量 |
|---|---|---|
| Run | `run_id, owner/session_id, context_version, poi, entry, travel_date, time_band, timezone, execution_mode, deadline` | 修改地点/入口/日期产生新版本；旧结果不能混进新报告 |
| Claim | `claim_id, original_text, normalized_claim, type, subject, predicate, quantifier, scope, source_span, decision_impact` | 每条尽量一个可检验谓词；“免费且免预约”拆开；保留“所有/通常/大约”等限定词 |
| EvidenceDocument | `evidence_id, url, final_url, publisher, source_type, title, quote, document_hash, fetched_at, published_at, occurred_at, valid_from/to, date_basis, access_status, provenance` | 抓取时间不能填进发布时间；未知时间保持 null；搜索摘要与原文分开 |
| ClaimEvidenceLink | `claim_id, evidence_id, stance, matched_scope, context_match, independence_group, excerpt_location, exclusion_reason` | 支持/反对是相对于 Claim 的关系，不是整篇文档的永久属性 |
| Verdict | `claim_id, context_version, label, reason, conditions, evidence_ids, countercheck, limitations, freshness, model/prompt/policy_version` | 标签必须由对应类型允许；证据 ID 全部可解析；不足也要明确缺什么 |
| Event/Job | `run_id, sequence, job_id, state, lease_until, attempt, context_version, payload` | 事件有序可重放；同一版本同一结果只提交一次 |

`provenance` 至少区分 `live_fetch / archived_snapshot / user_supplied / synthetic_fixture`。用户提交的宣传截图是**待核验材料**，不是独立支持证据。真实来源的历史快照与合成 fixture 是两类数据，不能共用一个含糊的“缓存”标签。

### 6.1 结论与执行状态分开

任务可为 `queued / extracting / awaiting_context / collecting / verifying / completed / partial / failed / cancelled`；Claim 有自己的执行状态。接口请求失败是 `source_unavailable` 之类的工具状态，不是事实标签 `CONTRADICTED`。

FACT/ROUTE 可用 `SUPPORTED / CONDITIONAL / CONTRADICTED / POSSIBLY_OUTDATED / INSUFFICIENT`。只有当前条件有足够支持时才用 CONDITIONAL；只有老原文与更新证据显示状态变化，或有效期明确已过时，才讨论过期。不能把“没抓到发布时间”归为过期。

CROWD 仍对应 PRD 的事实类展示状态，但必须带观察范围、样本来源和不确定性；不要把“存在排队反馈”扩张成“未来每个周末都拥挤”。EXPERIENCE 后续使用独立体验标签，MARKETING 输出指标或暂不核验。

### 6.2 例子：不要给 Claim 本身预埋答案

```json
{
  "claim_id": "c_route_1",
  "type": "ROUTE",
  "original_text": "地铁出来步行5分钟就到",
  "predicate": "walking_duration",
  "value": 5,
  "unit": "minute",
  "quantifier": "approximate",
  "context_version": 2,
  "origin_exit_id": null,
  "destination_entry_id": null,
  "missing_context": ["origin_exit", "destination_entry"]
}
```

这个对象应先请求确认/识别出入口，不能直接得到“地图显示 18 分钟”的预设结果。地图响应、单位转换和最终引用另外存储。

## 7. 三类 Claim 的核验策略

### 7.1 FACT：直接证据优先，但不是“官方永远最新”

先查目标 POI 当前官网票务/运营页面和日期适用的公告，再查政府/运营方发布渠道；公开售卖页面可提供商品状态，但不能用“没票”推导“闭园”。同时找关闭、收费区域、预约、施工、节假日特别安排等可能反驳原句的内容。

原文是“免费”时必须区分大门票、展馆/专类园、活动、停车、预约附带费用。若主体区域免费但目标体验区域收费，输出成立条件和收费范围。当前直接公告能解决问题就可停止，不强求再找两个转载。

本次真实例子：[上海植物园门票页面](https://www.shbg.org/sites/zhiwuyuan/InfoList.aspx?ctgId=70cd8e24-7067-475a-9898-f6964c3d98d1)写明“已于2022年起免大门票开放，售票专类园直接到专类园门口购票”。这可支持“免费”的范围区分，但页面未提供清晰更新日期，且本次没有穷尽查验临时安排，不能直接扩展为未来任意日期全园全项目免费。[S43]

更关键的是，官网“最新通告”入口本次返回的正文是 **2022-12-05 的防疫通知**。因此“官方来源 + 栏目名叫最新 + 今天抓到”也不足以证明当前有效。这是已经观察到的真实失败模式，必须进入演示和回归样例。[S42]

### 7.2 ROUTE：以真实出入口和路线计算为依据

使用高德 POI 搜索获得候选；保存 provider ID、城市、地址、坐标系和出入口。POI 2.0 文档列有 `children`、`entr_location`、`exit_location` 等扩展信息，但不保证每个 POI 都返回。[S20]

高德路径规划 2.0 的步行接口为 `GET /v5/direction/walking`。必须确认 `origin`/`destination` 的经度在前、纬度在后，使用同一坐标系；请求所需 `show_fields`，按**步行端点**返回结构提取米/秒，不混用驾车或旧版字段。保存原响应与请求时间，API Key 不进入证据或日志。[S19]

要点：

1. 比较地铁具体出口与景区可开放入口，不能使用站点中心到景区几何中心的直线距离。
2. 地图给的是估计路线时间，不包括购票、安检、排队和个体步速；这些限制随结论展示。
3. 原句未说出口时，评估合理候选。只有某个出口满足就说明条件；入口未知或开放状态未知则保留不足。
4. “约 5 分钟”与 6 分钟的微小差别不机械判冲突。先定义容差政策并用样本标定；与 18 分钟这种量级差异也必须有同一出入口依据。
5. 路线反证主要来自替代出口、实际入口与封闭/绕行公告，不必为追求形式另外搜几篇“步行 5 分钟”。

上海植物园交通页区分 1、3、4 号门，注明 4 号门可从轨道交通 3 号线石龙路站前往，并提示 2 号门停车场拆除。此页证明入口差异值得建模，**不能据它计算任何分钟数**；本次没有地图密钥，未取得实际路线响应。[S44]

### 7.3 CROWD：证据最弱、最需要诚实表达的一环

公开评论需要至少尽量取得 `poi/区域 + 原文 + 到访日期依据 + 时段 + 来源链接`。发布时间可能晚于到访日期；“昨天”只能在可靠发布时间下解析；只有“2026-09-xx 发表”而无到访信息，不能硬标成该周末的体验。

采用两组查询：支持侧查“周末、清静、人少、免排队”，反对侧查“周六/周日、排队、拥挤、限流、节假日”，再加入地点别名、入口和最近窗口。按候选中性检查，不能只挑反对内容制造“反转”。窗口可从近 30–60 天开始探索，但这是调参起点，不是时效性的通用定律。

先对真实到访日做日历匹配，区分普通周末、法定节假日、调休工作日；使用来源可追溯的年度假期配置，不能仅用 `weekday>=5`。同一 POI 不同入口、日落时段与上午、暑期与淡季分别处理。

输出示例应类似：“在已找到且能确认到访时间的近四个周末样本中，多个独立来源提到下午排队；不足以支持‘周末都不排队’，未来到访仍受天气和活动影响。”其中时间、数量必须由实际样本生成；没有就写不足。**评价样本有选择偏差，既不是实时客流，也不提供可靠的总体拥挤概率。**

一条高质量反例可以推翻“所有周末都不排队”这类绝对表述；不能据一条反例否定“通常人少”。对“通常”的判断需要更有代表性的证据，样本不足就保留不足。模型给出的“80% 可信度”不能伪装成统计结论。

未来接入携程后，订单/热度仍只是代理信号：订单可能包含取消、不同产品和不同履约日；没有容量、核销/入园等信息，不把订单数等同于人流量。

### 7.4 去重、充分性与停止条件

先做 canonical URL、正文 hash、近重复文本去重；再记录“明确引用同一公告/同一内容”的上游关系。多个域名搬同一公告只算一个信息根；身份与原创性不能确认时写“独立性未知”，不冒充完成假评论检测或完整传播链追踪。

每轮依次检查：地点/范围是否一致 → 时间是否适用 → 是否直接回答谓词 → 来源与第一手程度 → 与现有证据是否独立 → 是否出现未解释冲突。LLM 可提出关联建议，最终标签必须符合规则。

- 直接、当前、适用的权威公告已回答 FACT：记录反证检查后可结束。
- 高德路线与确认入口完整：可完成 ROUTE，同时保留路线估计限制。
- 只有转载、旧帖或场景不匹配评价：不能靠数量转成支持。
- 同等级、同时间、同场景证据仍冲突：再查一次上游/日期；仍无法消解则输出不足并展示冲突。
- 初始证据不足且预算剩余：只补查缺口，默认最多两轮；仍不足则停止。

不为来源权威性、时效、独立性设计一个未经校准的加权总分。可以记录这些可解释维度，但不要借公式掩盖未知。

## 8. 没有携程内部 API，公开采集怎样支撑 MVP

公开采集应成为后台证据能力。用户不需要关心抓取器，但结果必须显示原来源、适用时间和真实采集状态。所谓“后台抓取”不能在展示上变成“携程内部数据”。

### 8.1 三条接入路径

| 数据 | 首周做法 | 刷新与缓存 | 不可获得时 |
|---|---|---|---|
| 官方票价、开放、预约、施工公告 | 为试点 POI 配置官网/政府/运营方来源白名单；HTTP 定向抓取，正文和元数据抽取 | 高变化运营信息演示前复查；静态介绍可长缓存；有效期优先于固定 TTL | 展示最后采集时间、失效状态；不以旧快照声称当前开放 |
| POI、入口与步行路线 | 高德 Web 服务 API，必要时用户确认入口 | 查询键包括供应商、POI、起终点、交通方式、上下文版本；过期重新查 | 文档可读不等于 API 可用；未拿 Key 前只回放明确标注的路线响应样本 |
| 公开评价/游客叙述 | 搜索发现→逐篇取得正文→提取到访场景；只对实际可读来源定向适配 | 记录原始发布时间与到访日期；转载去重；检索窗口可配置 | 保留 CROWD 卡为证据不足；允许用户补充有出处的公开材料，但标明用户提供及独立性 |

对有限 POI 维护 `SourceRegistry`：域名、来源归属依据、允许路径、页面类型、parser_version、抓取频率、是否需 JS、更新时间抽取方法、最近成功和正文健康检查。首次来源归属由人工确认，避免“网页自称官方”就得到最高证据资格。

### 8.2 抓取工具比较

| 工具 | 适合的任务 | 成本/局限 | 建议 |
|---|---|---|---|
| httpx + Trafilatura / BeautifulSoup | 公告、新闻、简单页面正文与链接抽取 | 元数据/表格/图片需要额外处理；抽取正文成功不等于场景完整 | **默认**；站点特有票价表用专门解析器。[S45] |
| Playwright | 内容需要正常浏览器渲染才能显示的公开页面 | 内存、启动延迟、页面结构变化；也可能仍得不到正文 | 仅为明确站点调用，复用浏览器、限制并发和加载时长 |
| Crawl4AI | 封装浏览器、提取、Markdown 等采集流程 | 仍需要站点质量检查；引入框架不消除访问限制；README 署名措辞需结合 LICENSE 核对 | 作为第二选择，不与自写 Playwright 同时维护两套采集路径。[S36] |
| Firecrawl 托管 | 团队希望购买网页处理能力 | 增加外部依赖、调用费用；覆盖率须实测 | 可替换 Adapter；本次未付费验证中文站点覆盖。[S25] |
| Firecrawl 自托管 | 有持续采集需求且能承担部署 | 核心 AGPL-3.0、SDK 等另有许可；云端与自托管能力并非完全等同 | 首周不部署整套；不要因“开源”就假设复用无条件。[S25] |

正文、图片公告、PDF 分开处理：先提正文与日期；图片公告再走视觉/OCR，保留原图及页码/片段；不把视觉生成的转述当原文引用。只保留核验需要的公开摘录和允许保存的快照，不额外采集头像、联系电话、完整用户主页等无关信息。

搜索服务只负责发现候选。Tavily 支持域名和日期相关参数，可关闭生成答案、明确搜索深度；Perplexity Search API 也是候选。[S23] [S28] 默认先接一家，第一天在实际部署地区用相同中文查询比较有效正文命中率，再决定是否增加第二家。不要把浏览器抓取搜索结果页作为稳定生产搜索接口。

### 8.3 本次采集探查得到了什么

| 探查 | 实际观察 | 对架构的影响 |
|---|---|---|
| 上海植物园官网与门票/交通/通告页 | 可通过普通 HTTP 读出正文；门票存在范围条件；“最新通告”正文很旧 | 定向采集可行；必须有正文日期与范围判断。[S34] [S42] [S43] [S44] |
| 上海市政府新闻列表 | 可读到带日期的列表 | 可作为官方发现入口；本次没有据此取得景区即时闭园结论。[S33] |
| 一个携程公开景点 URL | HTTP 返回内容，但未得到可用的目标 POI 点评正文，存在通用页面内容 | 状态码 200 不能记为“评价采集成功”；不能承诺携程评论已经打通。[S35] |
| 两次普通搜索网页请求 | 返回内容与目标查询明显不相关 | 这两份页面不用于竞品结论；MVP 必须验证搜索服务相关性，不能只测连通性。[S38] [S39] |
| 高德文档、百炼文档 | 能确认公开接口/参数能力 | 未执行带密钥业务调用，配额、可用权限、部署地区延迟仍需首日验证。[S19] [S20] [S21] [S22] |

当遇到登录墙、验证码、403 或 429，将它作为可观测的来源不可用，采用可公开访问的其他来源、授权接口或用户提供材料；不把绕过限制作为 Demo 成功的依赖。按站点规则与可接受速率采集，限制重试，尊重明确访问限制。这里的直接工程收益是提高演示稳定性，避免把整周时间投入反爬维护。

### 8.4 首周 CROWD 数据闭环

第一天为候选 POI 检查评论能否取得正文、时间和上下文。优先选择有可追溯游客叙述且场景明确的地点进入核心演示，但保留至少一个“数据不足”案例，避免只挑容易得到确定答案的样本。

可以提前采集并人工核对一小批真实公开材料，建立快照集供回放；记录来源、采集日与原文，不人工编造评价。**回放验证管线稳定性，实时检索验证当前覆盖，两者分别报告。** 合成评论仅用于测试“重复转载”“缺日期”“工作日冒充周末”等逻辑，不用于真实 POI 的公开结论。

首周不能保证所有 POI 的 CROWD 都给出确定结果。如果无法获得足够评价，功能仍执行检索、反证和场景筛选，并返回具体缺口；这比伪造拥挤趋势更符合 PRD，也保留了未来内部数据的接入价值。

## 9. 编排、接口和失败恢复

### 9.1 一次任务怎样运行

1. 校验输入，生成 `run_id`，保存图片/文本；返回任务标识，不阻塞一个 HTTP 请求等待整份报告。
2. 视觉提取 3–5 条有决策价值的 Claim 和 POI 候选，保存原文定位。若存在多个地点，先让用户选择本次目标，暂不做多城市批量报告。
3. 确认地点、入口和出行场景。日期缺省时说明“按当前可获得信息核验”；涉及“本周末”等表达，必须按当地时区解析或确认，不静默承诺未来状态。
4. 按 Claim 并发检索；同一公告/POI 请求在一个任务内去重复用。模型/搜索/抓取分别设置并发限制。
5. 过滤不匹配证据、执行支持与反证检查，必要时补查一次；逐条生成受约束结果并落库。
6. 提交事件后推送卡片；用户可先阅读已完成项。报告总结只能引用已完成 Claim，不新增无出处内容。
7. 关键条件不满足时，从同城候选集筛选替代地点；复用核验结果说明满足哪些需求，未核验的属性显式标注。

### 9.2 最小 HTTP Interface

| 接口 | 行为 |
|---|---|
| `POST /api/runs` | 上传截图或提交文本/链接、可选出行上下文；返回 `run_id, state, context_version`；支持幂等请求键 |
| `POST /api/runs/{id}/context` | 确认/修改 POI、入口、日期；校验客户端版本，提交新版本并重算受影响 Claim |
| `GET /api/runs/{id}` | 当前版本完整快照，包括已完成和失败项 |
| `GET /api/runs/{id}/events` | SSE，包含 `event_id, context_version, claim_id, state`；只推送已落库事件 |
| `POST /api/runs/{id}/claims/{claim_id}/retry` | 只重试指定 Claim 的失败/缺口；保留历史与新 attempt |
| `GET /api/runs/{id}/evidence/{evidence_id}` | 原文摘录、来源、时间、适用场景、支持/反对关系及可访问原文链接 |

事件可以是 `input.parsed / context.required / claim.started / evidence.collected / claim.completed / claim.failed / run.completed`。展示用户可理解的进度，不输出模型内部推理文本，也不伪造百分比。

### 9.3 重启、并发和变更

MVP 用数据库任务表加租约，让一个 worker 领取任务；需要多 worker 时用原子领取/`SKIP LOCKED`，并发写入按 `run_id + context_version + claim_id + attempt` 做唯一约束。租约续期、attempt/fencing 检查防止过期 worker 覆盖新任务。外部请求可能重复执行，但结果提交幂等；这是 at-least-once，不宣称 exactly-once。

LangGraph 配持久化 checkpointer；RAM 中的 MemorySaver 不能支撑进程重启恢复。[S16] [S40] API 的 `BackgroundTasks` 本身也不等于可靠任务队列。checkpoint 管恢复位置，业务表是报告真相；关键结果提交与事件使用同一数据库事务，再发 SSE。

客户端断线用 Last-Event-ID/事件序号补读；也可定期读取完整快照。地点/日期变更后取消或逻辑废弃旧版本结果，迟到响应不能写回新卡片。反向代理关闭 SSE 缓冲并设置合理空闲时长，使用同源受控会话，不能把长期访问密钥放 URL 查询参数。

建议初始限制：单任务最多 5 条 Claim、同时处理 3 条、最多两轮检索、总外部搜索默认不超过 12 次、整体运行截止 120 秒。**这些是预算起点**，每次重试占同一预算；超过后保留已完成结果，未完成项明确原因。爬取站点超时与模型超时分别记录，避免多层各重试 3 次导致调用倍增。

### 9.4 数据输入安全属于功能可靠性

用户链接、搜索 URL、网页指令、OCR 内容全部当数据。抓取只接受 HTTP(S)，每次解析和重定向后检查地址，拒绝本地/私网/云元数据地址；限制跳转次数、响应大小、文件类型和下载时长。浏览器抓取运行在受限环境，不携带员工或用户登录态。

模型不得执行网页里的“忽略规则、调用工具、上传密钥”等指令；工具集合与参数由后端受控校验。原文引用需能匹配保存片段，证据链接由后端生成；HTML 清理后展示，不能直接注入前端。截图去除无关元数据，任务和证据按会话隔离，日志屏蔽 API Key、签名 URL 和无关个人信息。

## 10. 延迟、费用与资源预算

### 10.1 延迟预算是设计目标

| 阶段 | 初始预算 | 改进方向 |
|---|---|---|
| 上传、视觉解析、POI 候选 | 5–15 秒，目标 | 控制图片尺寸/输出长度；保留文字输入回退；以实测校准 |
| Claim 首轮证据 | 5–25 秒，目标 | 独立分支并发；同站限流；复用相同文档 |
| 场景匹配/裁决 | 3–12 秒，目标 | 确定性规则先筛选；只传必要原文 |
| 必要补查 | 额外 10–30 秒，目标 | 只补缺口，不整份报告重搜 |
| 第一张可读卡/整体报告 | 争取第一张 ≤25 秒；完整 45–90 秒；截止 120 秒 | 未实测，不向评委承诺固定响应时间 |

用户确认地点耗时单独记录；端到端性能从用户确认必要上下文后计，并另报从首次提交到结果的总时间，避免用口径掩盖等待。记录 p50/p95、冷启动/热缓存、3/5 条 Claim 和来源失败场景。少量样本的 p95 仅作演示观测，不视为线上 SLO 证明。

### 10.2 费用公式与有来源的锚点

```text
单次费用 = Σ(各模型输入 Token × 输入单价 + 输出 Token × 输出单价)
         + 搜索 credits × 单价 + 提取/浏览器费用 + 地图费用
         + 存储/带宽/主机摊销
```

视觉 Token、重试、思考 Token（若启用）、缓存命中、上下文阶梯和模型地域均应按供应商 usage 记录，不能仅按截图文件大小估算。

Tavily 本次官方文档写明：basic search 1 credit、advanced 2 credits，按量付费每 credit **US$0.008**，免费计划每月 1,000 credits。[S24] 因此一次 8 个 basic 搜索约 **US$0.064**，8 个 advanced 约 **US$0.128**；这只是搜索项，未包含提取、模型和地图。初期不要打开会自动改变搜索深度的配置后仍按 basic 计算。

百炼价格页按地域/模式/上下文分栏，且 alias 可能更新。[S27] 本报告不把网页上一个孤立数字当通用报价。举例说明计算方式：**假设**全流程 16,000 输入 Token、3,000 输出 Token，且统一假设价格为每百万输入 ¥1、输出 ¥4，则模型项为 `0.016 + 0.012 = ¥0.028`；这不是供应商报价，也未精确模拟视觉计费。开发时将真实模型/地域单价和 usage 代入。

100 次、每次 8 次 basic 搜索约 800 credits；若还有 2 次 basic 提取请求且每次提取成功 5 个 URL，再增加约 200 credits，恰好吃完 1,000 credits。反复调试、advanced 或超额都会增加费用，不能承诺整个黑客松免费。搜索通常值得优先设置预算上限；但是否是最大成本项仍取决于实际模型与抓取方式。

地图配额、商用要求和申请状态尚未核实到具体账号，列为第一天资源检查，不假设永久免费。服务器可先用现有开发机/团队主机；如需云主机，预留 ¥100–300 的短期开发预算仅是内部估算，不是云厂商报价。没有模型本地部署需求，首周无需购置 GPU。

## 11. 评测：证明比普通联网问答更有用

不能只展示一份看起来流畅的报告。黑客松要回答的是“更快获得有证据且影响决策的结论”，需要质量与耗时两类比较。

### 11.1 最小评测集与对照

建立 12 份截图/文本、约 36–48 条 Claim，FACT/ROUTE/CROWD 尽量均衡，包含支持、条件、冲突、可能过期、不足。按 POI 和来源切分开发集与保留集，避免同一截图换措辞当独立样本；人工标注原文、目标场景、可接受证据及结论理由，分歧记录并复核。

至少覆盖：同名 POI、错误入口、免费大门/收费区域、过期官方通知、普通周末与节假日、发表时间不等于到访时间、同一公告多站转载、近期但不同时间段、绝对表述与“通常”、无评价、来源超时、图片抽取漏字。

使用两类基线：

- **普通联网问答**：同一模型、相同输入、近似搜索预算，只要求回答并给来源；比较 Claim 级出处、场景错误和误判。
- **人工多平台查找**：至少 3 名试用者，任务交叉分配/顺序交换，计时到做出有依据的决策，而不是计时到出现第一行文字。小样本结果只报告观测，不做统计显著性宣传。

再做两个消融：关闭反证检索、关闭场景过滤。用它们说明具体设计贡献，而不把所有收益归因于“用了 Agent”。

### 11.2 指标与建议验收线

以下是开发验收目标，**目前没有跑出这些成绩**。

| 指标 | 如何计量 | 首周目标/门槛 |
|---|---|---|
| Claim 提取质量 | 与人工标注比对；避免把多个谓词合一 | 必选高决策价值 Claim 尽量全覆盖；报告 precision/recall 及漏项 |
| 类型路由 | FACT/ROUTE/CROWD 混淆矩阵 | ≥90% 是建议目标，不以全部标 FACT 蒙混 |
| 引用可追溯 | 每条结论引用能打开保存片段、定位原文 | 演示验收集 100%；原站失效也要区分保存快照 |
| 引用支持性 | 人工判断引文是否支持该理由及适用场景 | ≥95% 目标；反证不能被包装为支持 |
| 场景错误 | 把错 POI/错入口/工作日/旧通知当适用证据的次数 | 固定对抗用例必须为 0 |
| 严重误判 | 有直接高质量反证却输出“支持”的次数 | 固定验收集必须为 0，并报告样本数 |
| 证据不足校准 | 缺关键场景/只有转载时是否拒绝确定判断 | 所有预设缺证据用例正确保留不足 |
| 反证执行 | 每条有反证查询/结构化检查记录 | 100%；“查询无结果”与“未执行”区分 |
| 结论分类 | 人工标签与系统标签混淆矩阵 | 报告各类表现，不只报总体正确率 |
| 决策帮助 | 用户能否识别额外收费、错误距离、客流不确定性 | 记录正确决策率与理由，不只问“喜不喜欢” |
| 耗时/费用 | 每次运行 trace；人工对照计时 | 报告 p50/p95、调用数、单次费用；目标多数任务更快 |

一组几十条样本通过，只证明当前演示覆盖有效，不能声称产品整体“准确率 95%”。尤其要避免对每个关键指标都挑不同有利子集。

### 11.3 必须做的工程验收

测试应从 Module 的 Interface 进入，覆盖用户可见行为：

1. 修改日期/入口后旧版本结果不再更新当前卡片。
2. 来源 403/超时不影响已经完成的 Claim；能单条重试。
3. worker 在取证后重启，恢复任务且不重复提交结果；租约失效的 worker 不能覆盖新 attempt。
4. SSE 断线后可补读事件或读取快照，无需重新核验整份报告。
5. 一条公告被三站转载不增加三个独立支持来源；同一证据可对不同 Claim 有不同关系。
6. 含提示注入的网页、私网 URL、非法引用 ID 被拦截或降为无效数据。
7. 合成 fixture/历史回放不会带上“实时”标识；不存在从未取得的地图分钟数。

不用为每个样式或一行数据映射单独写测试；重点是会造成错误旅行结论、数据丢失或演示中断的行为。

## 12. 一周排期与演示策略

工作量按 2–3 人、约 7 天做规划估算。角色是工作分工，不代表已知团队构成。

| 日期 | 产品/前端 | 核验/后端 | 数据/集成/评测 | 当日可检查成果 |
|---|---|---|---|---|
| Day 1 | 3 个页面骨架，确认上下文流程 | 最小输入→Claim→结果契约；视觉与文本模型试测 | 选试点 POI，核实搜索/地图 Key，抓取 3 类来源样本 | 至少一个真实 FACT 从输入到引用；资源清单和数据缺口公开 |
| Day 2 | 上传、地点选择、结果卡和证据弹层 | 持久化、事件流、Claim 路由 | 官网采集与快照、POI/入口字段 | 截图解析 + FACT 真证据闭环，UI 与真实状态联通 |
| Day 3 | 路线结果与条件展示 | 高德路线 Adapter、单位转换、场景版本 | 验证两个入口场景，检查通告日期 | FACT + ROUTE 闭环；地点/入口修改后正确重算 |
| Day 4 | CROWD 样本范围与不足状态 | CROWD 对齐、去重、主动反证、充分性 | 标注真实评价和转载；补齐来源失败样例 | 三类 Claim 同屏，至少一个反证及一个不足案例 |
| Day 5 | 替代 POI 和真实页面跳转、异常交互 | 任务恢复、幂等、超时、成本记录 | 跑保留评测集与联网问答对照 | 可恢复的完整 Demo；第一份质量/延迟/成本记录 |
| Day 6 | 试用反馈与移动适配 | 修复高影响错误，冻结核心流程 | 人工查找对照、证据复查、部署环境演练 | 演示数据真实可追溯，关键用例全部过关 |
| Day 7 | 完整走台、录屏备份、讲解材料 | 只修阻断问题，验证线上依赖与限额 | 复查高变化公告，准备明确标注的快照回放 | 真实联网主链路 + 故障降级说明 + 可复核结果 |

若只有一人：减少到 3–5 个 POI、一个搜索供应商、官网一种静态解析器，H5 用成熟组件；优先保证三类 Claim 各有一个真实闭环，CROWD 证据不足也要正确执行并解释。砍掉复杂地图展示、第二模型供应商和花哨动画，不砍证据追溯、场景对齐或反证。

**首日关键路径是数据与访问权限，不是页面美化。** 若地图 Key 当天申请未完成，先用明确标记的 fixture 开发接口，但上线演示前仍必须做真实调用；拿不到就如实说明路线仅演示流程。若搜索服务在部署地区不可用，切换事先试测通过的供应商或试点官网定向检索，不能到 Day 7 才发现。

建议 3–4 分钟演示：

1. 上传一张含 3–5 条卖点的截图，确认 POI、入口和日期。
2. 先出现“免费但部分区域另收费”的条件卡，再展开原文。
3. 用真实地图响应说明路线是否满足宣传；分钟数现场取响应，不能预填。
4. 展示 CROWD 的支持/反对样本与场景筛选；可拿一条工作日反馈说明为何被排除。
5. 展示“最新通告实际是旧文”的失败案例，强调当前证据不足时会停止确定判断。
6. 保留用户原始需求，展示 1–2 个有证据说明的替代地点，进入有效 POI/门票页面。没有正式深链则使用可访问公开页面，并说明尚未接入内部交易链路。

演示的产品亮点是“错误证据被剔除，影响决策的条件被指出”，而非让每条卡片都有确定答案。不存在官方黑客松评分表材料，因此创新性、可用性、业务衔接只是这里建议呈现的维度，不写成比赛既定评分标准。

## 13. 赛后接入携程的演进路径

| 阶段 | 新增能力 | 触发条件与约束 |
|---|---|---|
| 公开数据 MVP | POI/入口、公开公告/评价、逐 Claim 核验、来源展示 | 首周交付范围；已知覆盖有限 |
| 内部数据接入 | POI 主数据、当前产品、房型/票种、真实履约后评价、可授权使用的热度信号 | 取得正式权限、字段字典与刷新 SLA 后再建设；通过 Adapter 输出统一 Evidence |
| 可信度与覆盖改进 | 证据抽样审计、领域评测集、缓存刷新、变更订阅、可解释冲突策略 | 有真实用户与误判记录，而非只看 Demo |
|规模化 | 独立采集队列、必要的 Redis/向量索引、横向 worker、对象存储、多区域策略 | 用采集量、队列延迟、检索评测和运维成本证明需求后再拆分 |

接入内部数据时首先解决：携程 POI 与地图 POI 的映射、酒店/房型/票种作用范围、评价的到访/入住日期、库存与运营状态的区别、用户权限与数据授权。没有这些字段，内部 API 并不会自动比官网证据更适用。

交易行动和核验结论分开：推荐或佣金因素不能改变事实标签；记录核验→展开证据→收藏/查看产品的转化即可，不在 MVP 自动下单。后续业务效果通过真实实验验证，不借用 TripGenie 的宣传数字作为目标预测。

## 14. 需要冻结的技术决策与剩余未知

| 决策 | 当前建议 | 什么证据会改变建议 |
|---|---|---|
| 语言与部署 | React/TS + Python 模块化单体，两类进程 | 若团队全员 TS 且 Python 零经验，可改全 TS；领域模型和规则保持 |
| 编排 | 小型 LangGraph 状态图 | 首日验证发现框架恢复成本高于显式状态机，保留同一 Interface 换实现 |
| 主模型 | 百炼中文视觉 + 文本，先测明确可用的组合 | 旅行截图错字、价格/日期遗漏、结构失败、部署地区延迟的实测 |
| 搜索 | 首接 Tavily，Perplexity Search 作为候选比较 | 中文/官网有效命中率、区域可达性、预算；不是品牌偏好 |
| 数据获取 | 定向官网 + 可访问公开评价 + 高德 | 取得携程正式数据权限或评价采集质量不达标 |
| 存储 | PostgreSQL + 文件卷；不先建向量库 | 文档规模及检索基线证明 embedding 有明显收益 |
| 产品成功条件 | 有证据、场景正确、能说明不足，且帮助更快决策 | 用户对照实验结果；不是生成报告长度或调用工具次数 |

待确认项：团队人数、预算与服务器位置、模型/地图/搜索账户可用性、首批城市/POI、比赛官方评分与提交流程。它们影响实施参数，**不妨碍当前完成选型调研**。最先验证的是：真实来源是否取得、场景字段是否足够、API 在实际部署环境是否可用。
