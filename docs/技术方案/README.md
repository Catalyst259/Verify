# 「验一下」技术方案总览

适用条件：一周黑客松、语言可选、暂无携程内部 API，使用公开通知、评价和地图数据。依据：[产品 PRD](../../验一下PRD.md)。方案日期：2026-09-29。

**推荐技术栈：React + TypeScript + Vite 移动 H5，Python + FastAPI 后端，LangGraph 编排，PostgreSQL 存储；接入官网定向采集、搜索 API 和高德地图。** 一个仓库，API 与后台 worker 两类进程，使用 Docker Compose 部署。

## 首版范围

选择一个城市的 5–10 个地点，每次核验 3–5 条 FACT、ROUTE、CROWD 主张。完整链路为：

```text
上传截图 → 确认地点与日期 → 提取主张 → 分类取证与反证
→ 时间场景对齐 → 逐条结论与来源 → 替代地点 / 旅行产品页面
```

核心差异是逐条核验、主动反证和场景对齐。不做地点统一可信度评分、完整全网爬虫、假评论识别或自动预订；主观体验和模糊营销表达留待后续。

最优先验证的是公开评价的可用性，以及模型、搜索、地图接口在部署环境中的可用性。当前为选型与设计结论，付费接口和性能指标尚未实测。
