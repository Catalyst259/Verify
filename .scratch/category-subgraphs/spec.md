# 补齐 ROUTE / CROWD / EXPERIENCE 三条类别子图

## Problem Statement

用户在小红书、抖音等平台被旅游种草后，无法判断种草内容里的具体说法**现在还成不成立**。「验一下」已经能做到「上传 MATERIAL → 提取 CLAIM → Fact 子图核验」，但 `CLAIMTYPE` 定义了四类主张，只有 `FACT` 一类真正跑通。

结果是：一条完整的种草里，「地铁步行 5 分钟」「周末人少」「适合日落」这三类直接影响旅行决策的说法，系统只能返回 `not_implemented`。用户拿到的是一份半成品报告——恰好漏掉了最容易过期、最容易夸大、主观性最强的三类信息。

对黑客松评委来说，这同样意味着 demo 只跑通了链路的四分之一。

## Solution

补齐 `ROUTE`、`CROWD`、`EXPERIENCE` 三条类别子图，让一次 `POST /api/verifications` 能对一条真实种草里的全部四类主张产出有证据、可追溯、用各自正确语义表达的判定。

三条新子图沿用 `FACT` 已验证的 `Plan → Search → Validate` 编排骨架，但**判定语义各不相同**：

| CLAIMTYPE | 判定语义 | 主要证据 |
| --- | --- | --- |
| `FACT` | 真假：支持 / 反驳 / 有条件 / 未验证 | 官方信息、产品数据 |
| `ROUTE` | 数值比对：主张时长 vs 实测时长 | 地图路线、POI、实际入口 |
| `CROWD` | 场景条件：主张是否在特定星期/节假日/时段/季节成立 | 近期同场景评价、客流信号 |
| `EXPERIENCE` | 体验一致性：较一致 / 明显分化 / 高度依赖场景 / 证据不足 | 近期真实游客与住客体验 |

同时，同一条 CLAIM 可能被多个子图选中（例如「地铁步行 5 分钟」会被 `FACT` 和 `ROUTE` 同时捞到）。系统必须让用户看见这些发现之间的**矛盾**，而不是各说各话。

## User Stories

1. 作为被种草的旅行者，我想把截图、文字和链接一起提交给系统，以便一次性核验整条内容而不是逐句手查。
2. 作为被种草的旅行者，我想让系统识别出种草里的每一条具体主张，以便我知道到底有哪些说法需要担心。
3. 作为被种草的旅行者，我想让「地铁步行 5 分钟」这类距离时间类主张被 `ROUTE` 子图核验，以便我知道宣传里的通勤时间是否可信。
4. 作为被种草的旅行者，我想让 `ROUTE` 子图给出实测步行时长与距离，以便我把「5 分钟」和「18 分钟」放在一起对比。
5. 作为被种草的旅行者，我想让 `ROUTE` 区分步行、驾车、公交等交通方式，以便「机场 10 分钟」不会被拿步行时间来反驳。
6. 作为被种草的旅行者，我想让 `ROUTE` 在起终点无法解析到具体 POI 时明确说「证据不足」，而不是拿一个猜测的坐标编造时长。
7. 作为被种草的旅行者，我想让「周末人少」「不排队」这类主张被 `CROWD` 子图核验，以便我知道种草描述的客流状况是否还成立。
8. 作为被种草的旅行者，我想让 `CROWD` 把星期、节假日、时段、季节作为核验条件保留下来，以便「周日下午不挤」不会被工作日上午的评价支持。
9. 作为被种草的旅行者，我想让 `CROWD` 在拿不到真实客流或交易信号时如实说明它用的是「近期公开评价密度」的近似，以便我不把近似值当成实测数据。
10. 作为被种草的旅行者，我想让「安静」「隔音好」「适合看日落」这类主张被 `EXPERIENCE` 子图核验，以便我知道主观卖点是否有多个独立来源支持。
11. 作为被种草的旅行者，我想让 `EXPERIENCE` 用「体验较一致 / 存在明显分化 / 高度依赖场景 / 证据不足」表达结论，以便我不被强行二元的真假判断误导。
12. 作为被种草的旅行者，我不想让主观体验被强判成「真」或「假」，因为这会制造系统并不具备的确定性。
13. 作为被种草的旅行者，我想看到每条主张的结论、理由和证据三级结构，以便我先看最影响决策的问题再决定要不要展开细节。
14. 作为被种草的旅行者，我想在证据不足时看到明确的「证据不足」而不是猜测结论，以便我知道这一条需要自己再查。
15. 作为被种草的旅行者，我想看到证据的来源、发布时间和抓取时间，以便我判断证据是不是过期了。
16. 作为被种草的旅行者，我想让支持证据和反证都被主动寻找，以便结论不是只挑对我有利的材料。
17. 作为被种草的旅行者，我想让同一条主张被多个子图核验时它们的矛盾被明确标出，以便我不被两份互相冲突的结论搞糊涂。
18. 作为被种草的旅行者，我想让主图在四条子图都跑完后给出完整的运行结果，以便我一次看完而不是分四次。
19. 作为被种草的旅行者，我想让某条子图失败时其他子图照常返回，以便一个环节出问题不会让整份报告报废。
20. 作为被种草的旅行者，我想让整个核验在一个可预期的时间内完成，以便我不用无限期等待。
21. 作为被种草的旅行者，我想让超时的子图明确标记为「执行失败」而不是假装「证据不足」，以便我区分「查不到」和「没查完」。
22. 作为种草内容的作者，我想让系统指出我内容里已经过期的说法，以便我知道哪些描述需要更新。
23. 作为行程规划者，我想让 `ROUTE` 的数值比对直接可读，以便我快速判断这段通勤时间能不能接受。
24. 作为行程规划者，我想让 `CROWD` 的结论带上具体场景条件，以便我判断这个结论是不是适用于我的出行时间。
25. 作为行程规划者，我想让 `EXPERIENCE` 的结论反映多个来源的一致程度，以便我知道这是普遍体验还是个别意见。
26. 作为行程规划者，我想让证据充分性被单独表达，以便我区分「结论是肯定的」和「结论只是暂时没被推翻」。
27. 作为维护者，我想让四条子图共用同一套编排骨架，以便修一处 bug 不用改四遍。
28. 作为维护者，我想让类别之间的差异收敛在「计划提示词、取证工具、判定词表」三处，以便新增第五类主张时不用动编排。
29. 作为维护者，我想让取证工具通过能力槽位注入，以便换地图供应商不改子图代码。
30. 作为维护者，我想让判定结构有明确的类型区分，以便新增类别时编译期就能发现没处理的分支。
31. 作为维护者，我想让浏览器并发有一个全局上限，以便四条子图并行时不会同时开十二个 Chromium 进程。
32. 作为维护者，我想让同一次运行内的重复查询只抓一次，以便一条种草的多类主张不会把同一批笔记翻三遍。
33. 作为维护者，我想让子图的失败、超时和诊断信息可追溯，以便出问题时能定位是取证失败还是判定失败。
34. 作为维护者，我想让 `FACT` 子图的现有输出在重构后保持不变，以便已有测试和前端不需要跟着改。
35. 作为黑客松评委，我想在一次演示里看到四类主张各自产出正确语义的判定，以便我确认这是完整的核验能力而不是单点 demo。
36. 作为黑客松评委，我想看到判定引用的真实证据链接，以便我确认结论不是模型编的。
37. 作为黑客松评委，我想看到系统的局限被明确标注而不是隐藏，以便我判断它的可信度边界。

## Implementation Decisions

### 判定结构：基类 + 子类收窄 + 判别联合

`Assessment` 基类承载四类共用的判定骨架，各类别子类收窄 `verdict` 词表并追加自己的字段。`FACT` 的既有字段与校验规则不动，只是多了一个父类。

`ClaimFinding.assessment` 的承载方式是本轮唯一的机制性决策。原型实测过三种方案：

```text
assessment: Assessment | None              序列化丢子类字段，反序列化正常
assessment: SerializeAsAny[Assessment | None]
                                         序列化保住，反序列化被 extra="forbid" 拒绝
assessment: Annotated[Fact | Route | ...,
             Field(discriminator="kind")]  双向都保住，已验证
```

判别联合是唯一能在 `model_validate` 从 dict 还原时保住子类字段的方案，而 `verification/graph.py` 与 `tests/test_frontend_results.py` 都真实走这条路径。因此采用带 `kind` 字面量字段的判别联合。

各子图的判定词表：

- `FACT`：`SUPPORTED` / `CONTRADICTED` / `CONDITIONAL` / `UNVERIFIED`
- `ROUTE`：`数值吻合` / `数值冲突` / `条件不符` / `证据不足`，并携带主张时长、实测时长、交通方式、误差范围
- `CROWD`：`当前证据支持` / `当前证据不支持` / `仅特定场景成立` / `证据不足`，并携带场景条件与证据的时间覆盖
- `EXPERIENCE`：`体验较一致` / `存在明显分化` / `高度依赖场景` / `证据不足`，并携带来源一致度

证据不足时不得给出确定结论——这一约束在 `FACT` 已有校验，三条新子图沿用。

### 编排骨架：从 FACT 抽取，四类共用

`FACT` 的 `initialize → plan ⇄ search → validate → finalize` 两轮编排、工具预算、回边判定、计时诊断、失败收束，对四类完全一致，抽成公共骨架。类别差异收敛到三个注入点：计划与判定提示词、取证工具集、判定词表模型。

轮数与调用预算保持 `FACT` 现有上限（两轮、每轮 20 次工具调用、5 次查询、15 份新增证据）作为四类的共同基线。`ROUTE` 不需要第二轮补搜时，其 `validate` 直接返回无缺口即可提前收束，不为对称而强行跑满。

`FACT` 改用公共骨架后，其输出 JSON 结构、字段和校验行为保持不变。

### 能力槽位：扩展既有 `VerificationCapabilities`，不新增注入机制

在已有的运行时能力容器中扩展：

- `place_resolver`：已有槽位，接入实现
- `map_routing`：新增槽位，抽象「坐标 → 时间/距离」，含单点路线、多点矩阵、步行可达圈
- `evidence_sources`：已有槽位，`xiaohongshu` 已落地
- 模型调用与搜索执行：由 `FACT` 专用的 `fact_llm` / `fact_search` 泛化为各子图共用的形状

`map_routing` 与 `place_resolver` 的接口按「坐标进、时间/距离出」定义，与具体供应商无关。

### 地图能力：开发期接免 key 公共服务，接口形状按可替换设计

演示阶段用 OpenStreetMap 生态：`Nominatim` 做地点解析，`Valhalla` 做路线、多点矩阵与步行可达圈。已实测中文 POI 解析可用、步行时长与距离可取、5 分钟/15 分钟步行圈可取。

这不是长期选择。公共服务有硬约束（路由每秒最多一次、脚本限单连接、要求可识别的 User-Agent、禁止把服务 URL 硬编码进应用），且其使用条款不允许商用产品把该服务作为重要组成部分。因此实现必须把供应商调用隔离在能力槽位之后，上线时替换实现而不动子图。

`ROUTE` 判定使用步行可达圈而非直线距离，以免「步行 5 分钟」被空气距离误判。

### 多子图同 claim 的冲突检测

`主图设计.md` 已明确「主图不按 CLAIMTYPE 过滤，向所有子图传递独立副本，由各子图自行选择」，且一条 CLAIM 允许有多项发现。本次不推翻该设计。

在此之上增加冲突检测：当同一条 CLAIM 的多项发现给出不相容的判定时，报告层必须显式标记矛盾，而不是并列展示让用户自己发现。判定语义不相容的判定对包括：数值比对冲突（如 `ROUTE` 判「实测 18 分钟」而 `FACT` 判「步行 5 分钟属实」）与真假/条件判定冲突。

### 并发与运行时预算

浏览器取证槽位设全局上限，四条子图共享，避免并发随子图数量线性增长。同时设运行级总超时兜住尾部，防止一条子图把其他子图饿死到各自超时。

证据源在单次运行内按查询键做记忆化。同一条种草的多类主张会各自发起查询，同一次运行内相同查询的材料只抓一次。

### 时区与时间对齐

`CROWD` 与 `EXPERIENCE` 的证据必须保留发布/采集时间，并与 `VerificationContext.checked_at` 及地点时区对齐。无法确定年份、对象或区域时保留为待查问题，不自行补成确定事实。

## Testing Decisions

### 什么算好测试

只测外部可观察行为，不测实现细节。具体禁止：编排节点顺序、字段是否存在、schema 是否定义、内部方法是否被调用、替身是否被调用、代码行数是否增长。这些照抄就能过，测了也拦不住真实缺陷。

要测的是消费者能看见的东西：判定词表是否正确、边界情况是否有正确语义、数值是否真的进了判定、矛盾是否真的被标出。

### 测试的 seam

**只用一个 seam：`VerificationService.run(VerificationInput) → VerificationRun`。**

这是最高可观察点。四类子图的新行为——verdict 词表、地图数值进判定、多子图同 claim 的冲突检测——全部在返回的 `VerificationRun` 里可观察。往上走 HTTP 层只是多套一层 DTO，新行为不在那里；往下测内部节点就是测实现细节。

不是 seam、只是注入旋钮的：`VerificationCapabilities`（模型调用、搜索执行、地点解析、证据来源、地图路由）与子图注册表。这些都是既有的注入点，`map_routing` 是往既有容器里加一个槽位，不新增注入机制。

### 会被测的模块与行为

- **判定词表边界**：`EXPERIENCE` 的「高度依赖场景」不得被判成「体验较一致」；证据不足时不得产出确定结论；`ROUTE` 的数值误差超出容差时必须是「数值冲突」而非「数值吻合」。
- **数值进判定**：注入地图路由替身返回实测时长，断言最终判定里同时出现主张时长与实测时长，且结论与两者一致。
- **冲突检测**：两个子图对同一 CLAIM 产出不相容判定时，断言报告层标记了矛盾。
- **失败隔离**：一条子图抛异常或超时，断言其他子图照常返回且整体不报废。
- **重构不改行为**：`FACT` 子图在改用公共骨架后，同一输入产出的 `SubgraphResult` 与重构前一致。

### 先例

- `tests/test_graph.py`：主图 + 脚本化子图 + 真实 LangGraph，覆盖完整 claim 列表分发、分支数据隔离、并行汇合、异常隔离。新子图的编排测试照这个形状。
- `tests/test_fact_workflow.py`：子图 + 注入的模型调用与搜索执行替身，覆盖判定校验、预算限制、失败收束。verdict 边界测试照这个形状。
- `tests/test_api.py`：HTTP 全链路，临时数据库。仅在 HTTP 契约改动时才用。
- `tests/test_fact_browser.py`、`tests/test_xiaohongshu_source_browser.py`：真实浏览器链路，由 `VERIFY_BROWSER_TESTS=1` 开关控制，用本地候选页与 HTTP 替身。

测试里的替身只用于验证链路，不代表真实模型的提取质量或真实公网搜索的可用性。

## Out of Scope

- **携程内部数据接入**（POI 库、票价、售卖状态、订单与热度信号）。演示阶段没有这些数据源，`CROWD` 用公开评价近似并在结果中标注。
- **生产地图供应商接入**（高德、百度、Google Maps）。演示阶段用免 key 公共服务，接口按可替换设计，但不实现供应商切换。
- **POI 消歧与入口选择**。「上海迪士尼乐园」可能对应多个入口，本次只做单点解析，不实现多候选择优。
- **报告生成、旅行推荐、替代 POI 建议、鉴权、任务队列**。这些在 `README` 与 `业务规则.md` 中标注为未实现，本次不做。
- **前端视觉重设计**。仅扩展判定词表的展示，不改交互与布局。
- **新增 `CLAIMTYPE`**。四类之外的主张类型不在本次范围，但编排骨架与判定基类要为后续新增留出位置。
- **评分系统**。系统不对地点生成统一可信度评分，只做逐 CLAIM 判定。
- **`main` 分支以外的协作流程改造**。提交仍走 fork + PR，issue 追踪已改为本地 markdown。

## Further Notes

### 本次实施中已做出、可被推翻的决定

以下决定是实施者在缺乏进一步输入时按既有约定与仓库现状推定的，若与预期不符直接修改本文件即可：

1. **测试 seam 定为一个**（`VerificationService.run`），不为地图数值单独开更底层的 seam。理由是该行为在最高点即可完整观察，多开 seam 会增加跨代码库的接缝数量。
2. **`CROWD` 接受「公开评价密度」作为客流的近似**，并在 `notes` 中如实标注。演示阶段拿不到真实客流/交易信号，这是唯一可行路径；若要求真实客流数据，`CROWD` 在本次应降级为 `not_implemented` 占位，范围需相应收缩。
3. **`FACT` 的重构以「输出完全不变」为验收线**，不趁机改进其提示词或判定质量。
4. **`.scratch/` 未加入 `.gitignore`**，因此 spec 会随 fork + PR 进入上游仓库。若需保持私有，应另行决定。
